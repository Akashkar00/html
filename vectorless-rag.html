01 / 24 — Foundations

What is Retrieval?

Before comparing architectures, you need to understand the exact problem retrieval solves: giving a language model access to facts it doesn't — and can't — already know.

🌀

Why LLMs Hallucinate

An LLM predicts the statistically likely next token — it has no built-in mechanism to say "I don't know." When facts are missing, it confidently generates plausible-sounding fiction.

📅

Knowledge Cutoff

Every model is trained on a snapshot of the internet up to a fixed date. Anything that happened after that — or was never public — simply doesn't exist to the model.

📏

Context Window

Even a huge context window is finite and expensive per token. You can't paste your entire company wiki into every prompt.

🗄️

External Knowledge

Private documents, live databases, and proprietary data were never in the training set at all — no amount of prompting recovers information that was never there.

🔗

The Need for Retrieval

Retrieval bridges the gap: find the right external facts at query time, and hand them to the model as grounding — instead of hoping it remembers correctly.

✅

The Payoff

A grounded model can cite sources, stay current, and say "I don't know" when the retrieved context doesn't contain an answer.

Evolution Timeline

Retrieval-augmented systems didn't appear overnight — they evolved through distinct generations, each solving the previous generation's limitations.

Raw LLM

Pure parametric memory. No grounding, no citations.

Prompt Engineering

Manually stuffing facts into prompts. Doesn't scale.

Traditional RAG

Hybrid Search

Knowledge Graph

Vectorless Retrieval

Agentic Retrieval

The model plans multi-step retrieval strategies itself.

Future

Self-improving, adaptive, multimodal retrieval systems.

🧬 Each generation fixed a real limitation of the last 🔮 Vectorless isn't a regression — it's a parallel branch, not a dead end
03 / 24 — Traditional RAG

Traditional RAG — Deep Explanation

Traditional RAG retrieves by meaning, not exact words — turning both documents and queries into vectors, then finding the closest ones in high-dimensional space.

🧮

Embedding Models

Neural networks (e.g. text-embedding-3, BGE, E5) that map text into a fixed-length vector where semantically similar text lands nearby.

✂️

Chunks & Chunking

Documents are split into smaller passages (chunks) — typically 200-800 tokens — because embedding models have limited input length and precision degrades on long text.

🏷️

Metadata

Each chunk carries metadata (source, page, date, author) used for filtering results before or after similarity search.

🗃️

Vector Database

A specialized store (Pinecone, Qdrant, Milvus, Weaviate) optimized for storing millions of vectors and searching them fast via approximate nearest neighbor indexes.

📐

Similarity Search

The query is embedded, then compared against every stored vector using cosine similarity, dot product, or Euclidean distance.

🔢

Top-K Retrieval

Only the K highest-scoring chunks (commonly 3-10) are kept — the rest are discarded before ever reaching the LLM.

🧱

Prompt Construction

Retrieved chunks are formatted and inserted into a prompt template alongside the user's original question and system instructions.

🤖

LLM Generation

The LLM reads the assembled context and generates an answer grounded in the retrieved passages rather than pure memory.

🏭

Production Pipeline

In production this whole flow runs behind caching, rate limiting, observability, and evaluation layers — not just a bare API call.

traditional_rag.py
def traditional_rag(query, vector_db, llm, k=5):
    # 1. Embed the query into the same vector space as the corpus
    query_vector = embedding_model.embed(query)

    # 2. Search the vector DB using cosine similarity (ANN index)
    top_chunks = vector_db.search(query_vector, top_k=k)

    # 3. Build a grounded prompt from the retrieved chunks
    context = "\n\n".join(c.text for c in top_chunks)
    prompt = f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"

    # 4. Generate a grounded answer
    return llm.generate(prompt)
🧮 Embeddings capture meaning, not exact words ✂️ Chunking is a necessary compromise, not a free choice 🔢 Only Top-K chunks ever reach the LLM's context

05 / 24 — Traditional RAG

What is Vector Search?

Every embedding is a point in a space with hundreds or thousands of dimensions. "Search" means finding the points closest to your query — fast, even across billions of them.

📍

Embeddings & High-D Vectors

A single vector (e.g. 1536 numbers) encodes the meaning of a sentence — similar meaning, similar direction in space.

🧭

Semantic Search

Matches by meaning: "car" and "automobile" land near each other even though they share no letters.

📐

Cosine Similarity

Measures the angle between two vectors — ignores magnitude, focuses purely on direction (meaning).

📏

Euclidean Distance

Straight-line distance between two points — sensitive to vector magnitude as well as direction.

⚡

Dot Product

A cheap, unnormalized similarity score often used internally by ANN indexes for speed.

🎯

ANN Search

Approximate Nearest Neighbor — trades a little accuracy for massive speedups versus checking every vector exhaustively.

🕸️

HNSW

Hierarchical Navigable Small World graphs — a layered graph structure that lets search "hop" toward the right neighborhood in O(log n).

🪣

IVF

Inverted File Index — clusters vectors into buckets first, then only searches the closest few buckets instead of the whole set.

🧰

Libraries & Databases

FAISS, ScaNN, Pinecone, Milvus, Qdrant, Weaviate, and Vertex AI Vector Search all implement variants of these ANN algorithms at scale.

📍 Meaning becomes geometry — similar ideas cluster together 🕸️ HNSW and IVF make billion-scale search fast, at a small accuracy cost
06 / 24 — Traditional RAG

Problems with Traditional RAG

Vector search is powerful, but it isn't free. Click any card below to expand the full explanation of each production pain point.

💸

Embedding Cost

▾
Every chunk must be embedded at index time, and every query embedded at search time. At millions of documents and constant re-indexing, embedding API costs compound quickly.
✂️

Chunking Problems

▾
There's no universally correct chunk size. Too small loses context; too large dilutes the embedding's precision and wastes tokens.
🧩

Lost Context

▾
Splitting a document into chunks can sever a table from its caption, or a clause from the sentence that defines it.
🛠️

Index Maintenance

▾
ANN indexes (HNSW graphs especially) need periodic rebuilding and tuning as data grows — they are not "set and forget."
⏱️

Latency

▾
Embedding the query is an extra network round-trip before search can even begin — adding tens to hundreds of milliseconds per request.
💾

Storage

▾
A 1536-dimension float32 vector is 6KB per chunk — multiplied across millions of chunks, storage costs quickly rival the source data itself.
🔁

Re-indexing

▾
Upgrading your embedding model means re-embedding your entire corpus — old and new vectors are not comparable.
📉

Version Drift

▾
Mixing vectors from two embedding model versions in one index silently corrupts similarity rankings.
📈

Cost Explosion

▾
Managed vector DBs bill by stored vectors and query volume — costs scale linearly (or worse) with corpus size and traffic.
🥶

Cold Start

▾
A brand-new corpus has no tuned index yet — early queries can be slower or less accurate until the index "warms up."
🎯

Poor Recall (Edge Cases)

▾
Exact identifiers — part numbers, error codes, legal citations — often embed poorly; semantic similarity doesn't capture "must match exactly."
🪓

Chunk Boundary Issue

▾
A fact split exactly across two chunk boundaries may not fully match the query in either chunk, dropping below the retrieval threshold in both.
🌫️

Semantic Gap

▾
Rare terminology, acronyms, or domain jargon may not be well represented in a general-purpose embedding model's training data.
🌀

Embedding Drift

▾
As language and usage evolve, a static embedding model's notion of "similar" can gradually stop matching real user intent.
👥

Duplicate Chunks

▾
Near-duplicate documents produce near-duplicate chunks, wasting Top-K slots on redundant results instead of diverse ones.
📚

Large Documents

▾
A 500-page manual becomes thousands of chunks — retrieval quality degrades as the corpus-to-relevant-chunk ratio grows more lopsided.
🖼️

Multimodal Issues

▾
Tables, charts, and images require specialized embedding models — text embedding models alone can't represent them well.
🔴

Live Data Problems

▾
Fast-changing data (prices, inventory, live scores) needs constant re-embedding and re-indexing — vector DBs are not built for real-time freshness.
💸 Embedding and storage costs scale with corpus size ✂️ Chunking is a lossy compromise with no perfect setting 🎯 Exact-match cases (IDs, codes) are a known weak spot
07 / 24 — Vectorless RAG

The Birth of Vectorless RAG

Long before embeddings existed, search engines were already excellent at finding relevant documents — using nothing but word statistics. Vectorless RAG is that lineage, refined for LLM grounding.

Why Remove Embeddings?

Researchers and engineers noticed that many of Chapter 7's problems — cost, latency, index maintenance, poor exact-match recall — all trace back to one root cause: the embedding step itself. Removing it removes the whole class of problems at once.

The History

Lexical retrieval (TF-IDF, then BM25) powered web search for decades before "RAG" was a term. When LLMs needed grounding, engineers realized these battle-tested, cheap algorithms could plug in directly — no GPU, no vector DB required.

The Motivation

Production teams wanted retrieval that was instantly explainable ("it matched these exact words"), cheap to run on commodity CPUs, and trivially easy to update in real time — properties classic vector search struggles with.

Modern Approaches

Today's vectorless systems combine BM25 scoring with structured metadata filters, knowledge graph traversal, and LLM-based re-ranking — a far cry from simple keyword matching alone.

Production Adoption

Enterprise search (legal, medical, code search), real-time systems, and cost-sensitive high-volume applications increasingly default to vectorless or hybrid retrieval rather than pure vector search.

When Vectors Become Unnecessary

When queries are precise (IDs, names, exact phrases), when data changes constantly, when cost per query must stay near-zero, or when full explainability is a hard requirement — vector search adds overhead without adding value.

📜 Lexical search predates embeddings by decades 🎯 Removing embeddings removes an entire category of failure modes 🏭 Production teams increasingly reach for it by default, not as a fallback
08 / 24 — Vectorless RAG

What is Vectorless RAG?

Vectorless RAG retrieves relevant documents using lexical and structural signals — matching words, statistics, and metadata — with zero embedding models and zero vector databases.

Definition

A retrieval architecture that finds relevant content through exact or statistical term matching (like BM25), structured metadata queries, or graph traversal — instead of embedding-based nearest-neighbor search.

🔤

Token / Keyword Matching

The simplest form: does the document contain the query's exact words? Fast, transparent, zero training required.

📊

BM25

A statistical ranking function scoring documents by term frequency, inverse document frequency, and length normalization — the gold standard of lexical search.

🌾

Sparse Retrieval

Represents documents as sparse vectors (mostly zeros) over the vocabulary — conceptually similar to embeddings, but interpretable term-by-term.

📖

Lexical Search

Any search matching literal text patterns — the umbrella term covering keyword, BM25, and phrase matching.

📇

Inverted Index

A map from every word to the list of documents containing it — the data structure that makes lexical search near-instant at scale.

🌲

Trie

A prefix tree used for fast autocomplete and prefix-matching queries over large vocabularies.

📃

Posting Lists

The per-word document-ID lists stored inside an inverted index — intersected together to answer multi-word queries.

🏆

Document Ranking

Once candidates are found, they're scored and sorted — by BM25 score, recency, popularity, or a blend of signals.

🧮

Hybrid Scoring

Combining multiple lexical signals (exact match + BM25 + freshness) into one final ranking score.

🏷️

Metadata Search

Structured filters — date ranges, categories, authors — narrow candidates before or after lexical scoring.

🕸️

Knowledge Graph Retrieval

Following entity relationships ("who reports to whom," "which parts belong to this assembly") rather than matching free text.

📐

Rule-Based & Structured Retrieval

Deterministic logic — "if query mentions an invoice number, look it up directly in the database" — bypassing search entirely for known patterns.

🚦

Document Routing

Classifying a query first, then sending it to the specific index or system best suited to answer it.

🔄

Dynamic Retrieval

Adjusting the retrieval strategy per-query — falling back to broader search when a narrow filter returns nothing.

BM25 Scoring, Visualized

BM25 rewards documents where query terms appear frequently, but with diminishing returns, and penalizes overly long documents.

vectorless_rag.py
def vectorless_rag(query, inverted_index, llm, k=5):
    # 1. Extract keywords/terms directly from the raw query — no embedding call
    terms = tokenize(query)

    # 2. Look up posting lists for each term in the inverted index
    candidates = inverted_index.lookup(terms)

    # 3. Score candidates with BM25 (term frequency + IDF + length norm)
    ranked = bm25_score(candidates, terms, top_k=k)

    # 4. Build a grounded prompt from the top-ranked documents
    context = "\n\n".join(d.text for d in ranked)
    prompt = f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"

    return llm.generate(prompt)
📇 Inverted indexes make lexical search sub-millisecond, even at scale 📊 BM25 is decades-old, battle-tested, and still extremely competitive 🕸️ Structured & graph retrieval handle exactness embeddings can't

14 / 24 — Hybrid

Hybrid RAG — Best of Both Worlds

Most mature production systems don't choose one paradigm — they fuse dense (semantic) and sparse (lexical) retrieval, then rerank the combined candidates.

🧮

Dense Retrieval

Embedding-based semantic search — great at conceptual, paraphrased queries.

📇

Sparse Retrieval

BM25 / lexical search — great at exact terms, codes, and rare vocabulary.

🔀

Fusion

Combining both result sets into one ranked list using a fusion algorithm.

🥇

RRF (Reciprocal Rank Fusion)

Scores each document by 1/(rank + k) summed across both retrievers — simple, robust, no score calibration needed.

🎯

Cross-Encoder Re-ranking

A small transformer scores (query, document) pairs jointly — far more accurate than similarity scores alone, at added latency cost.

🕸️

Graph Retrieval

Entity and relationship traversal supplements both dense and sparse results with structured facts.

🏷️

Metadata Filtering

Hard filters (date, permission, category) applied before or after fusion to enforce business rules.

🧭

Semantic + Lexical Together

Neither signal alone is complete — together they cover each other's blind spots.

🔀 RRF fuses two rankings without needing comparable scores 🎯 Cross-encoder reranking is expensive — apply it only to the fused shortlist

17 / 24 — Use Cases

When to Use Which?

Real-world recommendations by application type.

💬

Chatbot (General)

Hybrid Conversational queries are fuzzy and varied — dense retrieval handles paraphrasing while sparse catches exact product names or codes.

🏢

Enterprise Search

Hybrid Employees search both by concept and by exact document titles/IDs — hybrid covers both without compromise.

🎧

Customer Support

Vectorless Order numbers, SKUs, and ticket IDs dominate — exact lexical match plus metadata filtering outperforms semantic search here.

🩺

Medical AI

Traditional Clinical language varies hugely in phrasing for the same concept — semantic retrieval is essential, paired with strict metadata filters.

⚖️

Legal AI

Graph + Vectorless Legal citations must match exactly, and case relationships are structural — graph and lexical search beat pure vector similarity.

💰

Finance

Vectorless Ticker symbols, account numbers, and regulatory codes need exactness; live pricing data needs real-time indexing — vector DBs struggle with both.

👨‍💻

Code Assistant

Hybrid Symbol/function names need exact match; conceptual "how do I..." queries need semantic search — both matter.

🔬

Research Assistant

Traditional Research queries are inherently conceptual and cross-disciplinary — semantic retrieval finds related ideas across different terminology.

🕹️

RAG Agent (Multi-Step)

Graph + Hybrid Agentic systems benefit from structured knowledge graphs for planning, backed by hybrid retrieval for each sub-step.

🎯 Structured identifiers → lean vectorless 🧭 Conceptual, varied phrasing → lean traditional / semantic 🤝 Uncertain or mixed? Default to hybrid
18 / 24 — Pitfalls

Common Mistakes

Every one of these has degraded a real production retrieval system.

📏

Wrong Chunk Size

Too small loses context, too large dilutes relevance — teams often pick a size once and never revisit it as content changes.

🏷️

Poor Metadata

Missing or inconsistent metadata (dates, source, permissions) makes filtering — and access control — nearly impossible.

🏆

No Reranker

Raw similarity or BM25 scores alone are a weak final ranking signal — skipping reranking leaves easy accuracy on the table.

📚

Too Many Chunks (Top-K too high)

Stuffing the context window with marginal chunks dilutes the signal and increases cost without improving answers.

🙈

Ignoring BM25

Teams often assume "vector search is strictly better," missing easy wins on exact-match queries that BM25 handles natively.

🧮

Using Only Vectors

Pure vector search alone consistently underperforms hybrid approaches on real-world query distributions.

🧪

No Evaluation

Shipping a retrieval pipeline without a labeled eval set means you can't measure regressions when you change chunking, models, or K.

⚡

No Caching

Re-embedding or re-searching identical or near-identical queries repeatedly wastes latency and money.

📡

No Observability

Without logging retrieved chunks, scores, and final answers, debugging a bad response becomes pure guesswork.

🧪 If you can't measure it, you can't improve it
19 / 24 — What's Next

The Future of Retrieval

Retrieval is still evolving fast. Here's where the field is heading.

🕹️

Agentic Retrieval

The model plans its own multi-step retrieval strategy, deciding what to search for next based on what it's already found.

🕸️

Graph RAG

Knowledge graphs and vector search fused, so retrieval understands both meaning and structural relationships.

🧠

Memory RAG

Retrieval systems that build persistent memory of a user or conversation over time, not just per-query.

🖼️

Multimodal RAG

Unified retrieval across text, images, audio, and video in a single ranked result set.

📏

Long Context Models

As context windows grow, retrieval shifts toward "find the right documents," leaving "reasoning over them" to the model itself.

🗜️

Context Compression

Retrieved content is summarized or distilled before insertion, maximizing signal-per-token in the prompt.

🗺️

Retrieval Planning

Systems that decompose complex questions into sub-queries, retrieve for each, then synthesize.

🔄

Adaptive Retrieval

Dynamically choosing vector, lexical, or graph retrieval per-query based on the query's own characteristics.

♻️

Self-Improving Retrieval

Systems that learn from user feedback and downstream outcomes to continuously re-tune ranking and retrieval strategy.
