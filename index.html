What is Infrastructure as Code?

Before touching a single line of Terraform, you need to understand the problem it solves: turning infrastructure — servers, networks, databases — into something you can write, review, and version like software.

1. Definition

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable definition files, rather than manual configuration or interactive tools.

2. Why It Exists

Manual infrastructure doesn't scale, isn't reproducible, and leaves no audit trail. A team of 3 engineers can't safely hand-click hundreds of resources across dev, staging, and production without drift and human error creeping in.

3. Real Analogy

Manual cloud configuration is like assembling IKEA furniture from memory, every single time, in every room of the house — never writing down the steps. IaC is the instruction manual: repeatable, shareable, and diffable when something changes.

4. Enterprise Explanation

Enterprises need consistent environments across dozens of teams and regions. IaC gives them a single source of truth, code review for infrastructure changes, and the ability to reproduce entire environments in minutes — not days.

5. Production Explanation

In production, IaC is what makes disaster recovery realistic. If a region goes down, you don't rebuild by hand — you run terraform apply against a new region using the exact same definitions that built the original.

Treating the console as a "quick fix" — even one manual change starts configuration drift that Terraform can't see until the next plan.

Best Practice

Because it provides reproducibility, version control, peer review, and audit trails for every infrastructure change — eliminating the "it worked when I clicked it" problem.

What is Terraform?

Terraform is HashiCorp's open-source IaC tool. It lets you describe desired infrastructure state in configuration files, then figures out exactly what API calls are needed to make reality match that description — across almost any cloud provider.

HashiCorp

The company behind Terraform, Vault, Consul, and Packer. Terraform launched in 2014 and became the de-facto multi-cloud IaC standard.

Providers

Plugins that translate Terraform's generic resource language into specific API calls — e.g. the google provider talks to GCP.

Resources

The actual infrastructure objects you declare — a Cloud SQL instance, a VPC, an IAM binding, a Cloud Run service.

Desired State vs Actual State vs Drift

Terraform's entire model rests on comparing three things: what your code says should exist, what your state file last recorded, and what actually exists in the cloud right now.

Execution Plan

terraform plan computes the diff between state and code, producing a preview of adds, changes, and destroys — before anything happens.

Dependency Graph

Terraform builds a directed graph of resources so it knows what must be created (or destroyed) before what — explored fully in Chapter 11.

Modules

Reusable, parameterized bundles of resources — the "functions" of Terraform, letting you compose infrastructure like software.

Variables & Outputs

Variables parameterize configuration; outputs expose values (like a deployed URL) for humans or other automation to consume.

Backends

Where the state file lives — locally, or remotely in GCS / S3 for team collaboration and locking.

Why This Separation Matters

Terraform Core knows nothing about GCP, AWS, or Azure. It only understands the generic resource graph, state, and diffing algorithm. Providers are the plugins that know how to translate a google_sql_database_instance block into real REST calls against sqladmin.googleapis.com. This is why the same Terraform core can manage over 3,000 providers.

Common Mistake

Assuming Terraform Core talks directly to GCP. It never does — the provider plugin is always the translator, and provider version pinning matters because behavior can change between versions.

Best Practice

Pin provider versions explicitly in provider.tf so a `terraform init` next month doesn't silently pull a breaking provider update.

InterviewWhat's the difference between Terraform Core and a Provider?
Terraform Core handles the generic engine: parsing HCL, building the dependency graph, diffing state, and orchestrating execution. Providers are plugins that implement CRUD operations for a specific API (like Google Cloud), translating abstract resource blocks into real API calls.
User → CLI → Core → Provider → Cloud API → Resources Core is cloud-agnostic; providers are cloud-specific

Terraform Lifecycle

Five commands take you from an empty directory to running infrastructure. Click each one to see what happens internally.

~/terraform

What Happens Internally

terraform init downloads the provider plugins declared in provider.tf into .terraform/, and configures the backend that will store state.

Common Mistake

Running terraform apply without ever reading the plan output — the plan is your last chance to catch an accidental resource destroy.

Best Practice

Always run fmt and validate in CI before plan, and require a human to review the plan before apply in production.

InterviewWhat is the difference between terraform plan and terraform apply?
plan is read-only — it computes and displays the diff between desired and current state without making any changes. apply executes that plan, making real API calls to create, update, or destroy resources.
init → validate → fmt → plan → apply → destroy plan is a dry run; apply is the real thing

Why Split Into Multiple Files?

Terraform doesn't care how you split files — it loads every .tf file in a directory and merges them into one configuration. Splitting by concern (networking vs database vs compute) is a human convenience: it makes the codebase reviewable, so a database change and a Cloud Run change show up in different, focused files during code review.

provider.tf

provider.tf
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.30"
    }
    time = {
      source  = "hashicorp/time"
      version = "~> 0.11"
    }
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

Declares the two providers this project needs: google for every GCP resource, and time — used purely to insert an artificial delay (see Chapter 12's Eventarc race condition). Version constraints are pinned with ~> so a minor version bump can't silently break the plan.

main.tf

main.tf
// Private network for Cloud SQL, Redis & Cloud Run egress
resource "google_compute_network" "vpc" {
  name                    = "${var.project_id}-vpc"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "subnet" {
  name          = "${var.project_id}-subnet"
  ip_cidr_range = "10.10.0.0/24"
  region        = var.region
  network       = google_compute_network.vpc.id
}

// GCS buckets for raw documents & ingestion staging
resource "google_storage_bucket" "documents" {
  name          = "${var.project_id}-documents"
  location      = var.region
  force_destroy = false
}

// Redis for caching / short-term session & embedding cache
resource "google_redis_instance" "cache" {
  name               = "${var.project_id}-redis"
  tier               = "BASIC"
  memory_size_gb     = 1
  region             = var.region
  authorized_network = google_compute_network.vpc.id
}

// Artificial delay so dependent IAM bindings don't race
resource "time_sleep" "wait_for_sa" {
  depends_on      = [google_project_service.eventarc]
  create_duration = "60s"
}

This is the "foundation" file: the private VPC and subnet, the storage buckets that hold raw documents, the Redis cache, and IAM bindings shared across services. It also defines the notorious time_sleep resource that we'll dissect fully in Chapter 12.

cloud_run.tf

cloud_run.tf (excerpt — backend service)
resource "google_cloud_run_v2_service" "backend" {
  name     = "${var.project_id}-backend"
  location = var.region

  template {
    scaling {
      min_instance_count = 1
      max_instance_count = 10
    }
    vpc_access {
      network_interfaces {
        network    = google_compute_network.vpc.id
        subnetwork = google_compute_subnetwork.subnet.id
      }
      egress = "PRIVATE_RANGES_ONLY"  // Direct VPC Egress — Ch. 9
    }
    containers {
      image = "${var.artifact_registry}/backend:latest"
      env {
        name  = "DB_SOCKET_PATH"
        value = "/cloudsql/${google_sql_database_instance.main.connection_name}"
      }
    }
  }
}

Four near-identical blocks define backend, UI, ingestion, and evaluation services. Each uses vpc_access with PRIVATE_RANGES_ONLY egress — Direct VPC Egress, no VPC connector needed — and reaches Cloud SQL over a Unix socket rather than TCP.

ingestion.tf

ingestion.tf
resource "google_eventarc_trigger" "on_upload" {
  name     = "${var.project_id}-ingestion-trigger"
  location = var.region

  matching_criteria {
    attribute = "type"
    value     = "google.cloud.storage.object.v1.finalized"
  }
  matching_criteria {
    attribute = "bucket"
    value     = google_storage_bucket.documents.name
  }

  destination {
    cloud_run_service {
      service = google_cloud_run_v2_service.ingestion.name
      region  = var.region
    }
  }

  service_account = google_service_account.eventarc_sa.email
  depends_on      = [time_sleep.wait_for_sa]  // avoids the IAM race — Ch. 12
}

Whenever a document lands in the documents bucket, Eventarc fires an event that directly invokes the ingestion Cloud Run service. This file explicitly depends_on the time_sleep resource from main.tf to dodge a real IAM propagation race condition.

variables.tf

Declares every input: project_id, region, db_user, db_password, artifact_registry — with types, descriptions, and sensible defaults where safe.

terraform.tfvars

The actual secret values fed into those variables for this environment. Git-ignored, never committed — explored deeply in Chapter 13.

output.tf

Exposes backend_url, ui_url, evals_url, and ingestion_url after apply — the URLs a human (or CI) needs next.

main.tf feeds the VPC into database.tf and cloud_run.tf. database.tf feeds a connection name into cloud_run.tf. cloud_run.tf feeds service names into ingestion.tf.

Cloud Run Architecture

Four independent Cloud Run services, each scaled and exposed differently based on what it actually does.

Backend

The core API. Handles retrieval, chat orchestration, and query routing. Scales 1→10 instances, private-only egress to Cloud SQL/Redis/Qdrant.

UI

The user-facing frontend. Publicly accessible, talks to Backend over HTTPS — never touches the database directly.

Ingestion

Invoked only by Eventarc when a document lands in storage. No public entry point — internal-only invocation.

Evaluation

Runs RAG quality evaluations (retrieval accuracy, answer relevance) on a schedule or on-demand — kept isolated from the request-serving path.

Why Four Separate Services Instead of One?

Splitting by responsibility means each service scales independently — a spike in chat traffic doesn't starve the ingestion pipeline of CPU. It also means a bug in evaluation code can never take down the user-facing UI, and each service can have its own least-privilege service account.

Public vs Internal Traffic

UI
public ingress
Backend
internal ingress
Ingestion / Eval
internal ingress

Only the UI accepts ingress = "all". Backend, Ingestion, and Evaluation use ingress = "internal", reachable only from other GCP services within the same project or via Eventarc.

Common Mistake

Leaving Backend's ingress as "all" out of convenience. This exposes an internal API directly to the internet, bypassing the UI's auth layer entirely.

Best Practice

Default every Cloud Run service to internal ingress, and only widen to all for the one service that truly needs public access.

09 / 22 — Networking & Data

Networking

How does a Cloud Run container — a public-facing, serverless container — reach a database that has no public IP at all? The answer is Direct VPC Egress.

Direct VPC Egress

Cloud Run attaches directly to a VPC subnet without any intermediary — no VPC Connector required. Traffic leaves the container and enters the VPC natively.

Private IP Only

Cloud SQL, Redis, and Qdrant are all configured with ipv4_enabled = false — they simply don't have a public address to attack.

Direct VPC Egress vs Legacy VPC Connector

Legacy: VPC Connector

  • Requires provisioning & paying for a separate connector resource
  • Adds a network hop → extra latency
  • Connector has its own scaling limits & cost

Direct VPC Egress

  • No connector resource — nothing extra to provision or pay for
  • Lower latency: one fewer hop between container and VPC
  • Scales with Cloud Run itself, no separate bottleneck

Packet Flow Animation

No connector, no NAT gateway, no public hop — the Cloud Run instance's egress interface lives directly on the subnet.

InterviewWhy is Direct VPC Egress cheaper and faster than a Serverless VPC Connector?
A VPC Connector is itself a small managed instance group you provision, scale, and pay for — and all traffic must be proxied through it, adding a hop. Direct VPC Egress attaches network interfaces straight to the Cloud Run revision, removing that extra resource and hop entirely, which cuts both cost and latency.
Direct VPC Egress = no connector, no NAT, lower latency Databases have zero public IPs

Cloud SQL Connection

Cloud Run doesn't open a TCP connection to Cloud SQL's IP. It talks through a Unix socket, backed by an auto-managed Cloud SQL Auth Proxy sidecar.

Cloud Run Container
Unix Socket
/cloudsql/CONNECTION_NAME
Cloud SQL Auth Proxy
automatic, encrypted
Cloud SQL — PostgreSQL 15
cloud_run.tf (connection env vars)
env {
  name  = "DB_SOCKET_PATH"
  value = "/cloudsql/${google_sql_database_instance.main.connection_name}"
}

// application connects using this socket path — never a TCP host:port

Why Not Plain TCP?

TCP to a private IP would still require the container to be on the same VPC and would need manual TLS certificate management. The Unix socket approach lets Cloud Run's platform automatically manage an encrypted, authenticated tunnel with zero extra Terraform for certificates.

Security Benefit

IAM controls exactly which service accounts may open the socket — there's no password-guessable network endpoint exposed at all, public or private.

Terraform Wiring

The connection is only possible because cloud_run.tf reads google_sql_database_instance.main.connection_name — an attribute Terraform doesn't know until database.tf's resource is actually created. This creates an implicit dependency: Terraform automatically builds Cloud SQL before wiring up any Cloud Run service that references it.

InterviewWhat Terraform mechanism guarantees Cloud SQL exists before Cloud Run tries to reference its connection_name?
An implicit dependency. Because the Cloud Run resource block references google_sql_database_instance.main.connection_name, Terraform's dependency graph automatically places the SQL instance before the Cloud Run service in creation order — no explicit depends_on needed.
Unix socket, not TCP host:port Cloud SQL Auth Proxy is automatic on Cloud Run Attribute references create implicit dependencies

Eventarc Race Condition

A real bug this project hit in production planning: enabling the Eventarc API creates a Google-managed service account — but IAM bindings against that account can fail if applied too fast.

Why the Service Account Doesn't Exist Immediately

When google_project_service.eventarc is enabled, Google Cloud asynchronously provisions a service agent (service-PROJECT_NUMBER@gcp-sa-eventarc.iam.gserviceaccount.com) behind the scenes. Terraform's API call to enable the service returns successfully before that service account has fully propagated through Google's IAM backend — so an immediate IAM binding against it fails with a "service account does not exist" error.

API Enabled
google_project_service.eventarc
Waiting
time_sleep.wait_for_sa (60s)
Service Account Created
Google IAM backend catches up
IAM Granted Successfully
google_eventarc_trigger.on_upload
main.tf — the fix
resource "google_project_service" "eventarc" {
  service = "eventarc.googleapis.com"
}

resource "time_sleep" "wait_for_sa" {
  depends_on      = [google_project_service.eventarc]
  create_duration = "60s"  // gives Google's IAM backend time to catch up
}

resource "google_eventarc_trigger" "on_upload" {
  // ...
  depends_on = [time_sleep.wait_for_sa]  // explicit dependency — no attribute to reference
}

Common Mistake

Re-running terraform apply repeatedly hoping the race resolves itself. It often does on retry #2 — masking the real issue instead of fixing it deterministically.

Best Practice

time_sleep is a pragmatic, explicit fix for known async-provisioning races. It's not elegant, but it's honest — the alternative is a flaky pipeline nobody trusts.

InterviewWhy can't Terraform's dependency graph alone fix this Eventarc race condition?
The dependency graph only guarantees the order of Terraform API calls, not the propagation delay inside Google's own backend after an API call returns "success." The service enablement call returns immediately, but the resulting service account may not be queryable by IAM for several seconds — a timing issue outside the graph's visibility, which is exactly what time_sleep compensates for.
Enabling an API can trigger async, delayed service account creation time_sleep + depends_on is the pragmatic fix Retrying blindly hides the root cause

Deployment Workflow

There's a subtle chicken-and-egg problem: Cloud Run needs a container image to deploy, but the image needs somewhere to live first. This project solves it with a two-phase apply.

terraform init
terraform apply
Artifact Registry only
Cloud Build
builds container images
Docker Images
pushed to Artifact Registry
terraform apply
full stack — Cloud Run, SQL, VPC...
Cloud Run Services Live
Outputs Printed
backend_url, ui_url...

Why Artifact Registry First?

A google_cloud_run_v2_service resource requires an image field pointing at a real image URI. If that image doesn't exist yet, apply fails. So the registry (a cheap, dependency-free resource) is applied first, Cloud Build populates it with real images, and only then does the second apply provision Cloud Run against images that now actually exist.

Common Mistake

Trying to do it all in one apply with a "latest" tag and hoping Cloud Build finishes first — race conditions between build and deploy are a classic CI/CD trap.

Best Practice

Tag images with the Git commit SHA, not latest, so every Terraform apply is deterministic and reproducible.

Registry first, then build, then full apply Solves the chicken-and-egg image dependency problem

Refresh pulls Real GCP → State File. Plan diffs Config against State File. Apply pushes Config → Real GCP, then updates State File.

Remote Backend

State is stored in a GCS bucket (with versioning enabled) instead of a laptop's disk — so the whole team shares one source of truth, and a lost laptop doesn't mean a lost state file.

State Locking

The remote backend also locks state during an apply, preventing two engineers from corrupting it with simultaneous writes.

Common Mistake

Deleting terraform.tfstate to "start clean." This doesn't delete the real cloud resources — it just makes Terraform forget about them, leading to duplicate resources or apply errors.

Best Practice

Always use a remote backend with versioning and locking for any team or production configuration — local state is fine only for solo experiments.

InterviewWhat happens if you manually delete a resource in the GCP Console that Terraform manages?
Terraform's state still lists it as existing. On the next plan or refresh, Terraform detects it's missing from the real infrastructure and will propose recreating it — this is drift detection in action.
State is Terraform's only memory of reality Remote backends add sharing + locking Never hand-delete the state file

Common Mistakes

Every one of these has broken a real production apply somewhere. Learn them once, avoid them forever.

Manual Changes in the Console

Clicking a "quick fix" directly in GCP Console creates invisible drift that the next plan will fight against — or worse, silently revert.

Hardcoded Values

Baking a project ID or region directly into a resource block makes the config impossible to reuse across environments.

Deleting the State File

Doesn't delete real infrastructure — just makes Terraform blind to it, usually resulting in duplicate resource errors on the next apply.

Missing depends_on

Forgetting an explicit dependency for resources with no attribute link — like the Eventarc service account race from Chapter 12 — causes intermittent apply failures.

Ignoring Outputs

Manually hunting for a Cloud Run URL in the console instead of reading terraform output wastes time and invites typos.

Not Pinning Providers

An unpinned provider can silently jump a major version on the next init, changing resource behavior without a single code change.

Every mistake above traces back to skipping review or process

Interview Questions

Click any question to reveal a model answer, organized from beginner to production-scenario difficulty.

BeginnerWhat is the difference between Terraform and a configuration management tool like Ansible?
Terraform is declarative and focused on provisioning infrastructure (creating/destroying cloud resources), maintaining state of what exists. Ansible is more commonly used for configuration management on already-provisioned machines (installing packages, editing config files) and is more procedural/imperative in style, though both can overlap.
BeginnerWhat file extension do Terraform configuration files use?
.tf for HCL configuration, and .tfvars for variable value files. State is stored in .tfstate (JSON).
IntermediateWhat is the difference between a Terraform module and a resource?
A resource is a single infrastructure object (one Cloud SQL instance, one bucket). A module is a reusable, parameterized collection of resources — potentially dozens — that can be instantiated multiple times with different inputs, like a function call in programming.
IntermediateHow does Terraform decide the order in which resources are created?
It builds a directed acyclic graph (DAG) from implicit dependencies (attribute references between resources) and explicit depends_on declarations, then walks the graph to create independent resources in parallel and dependent ones in order.
AdvancedWhy would you use a remote backend instead of local state, and what problem does state locking solve?
Remote backends (like GCS) let a team share one state file, add versioning/rollback, and enable locking. Locking prevents two people from running apply simultaneously, which could otherwise corrupt the state file or produce conflicting resource changes.
AdvancedWhat's the difference between "tainting" a resource and destroying it?
Tainting marks a resource for recreation on the next apply (destroy then create) while keeping it in your configuration. Destroying via terraform destroy removes it entirely and drops it from both the config's active resource set and, after apply, the state.
ScenarioYour `terraform apply` fails halfway through, creating some resources but not others. What do you do?
First, don't panic or delete state. Run terraform plan to see the current diff — Terraform already recorded the partially-created resources in state. Fix the underlying error (e.g. a quota limit or IAM permission), then re-run apply; Terraform will resume from where it left off, only touching what's still needed.
ScenarioA teammate manually deleted a Cloud Storage bucket that Terraform manages. What happens on the next plan?
Terraform refreshes state, notices the resource no longer exists in GCP, and will plan to recreate it. If the bucket held critical data, this is also your case study for why lifecycle { prevent_destroy = true } and bucket versioning matter.
ProductionHow would you structure Terraform for a project with dev, staging, and prod environments?
Typically: shared modules in a common directory, and separate state per environment — either via distinct directories with their own backend config, or Terraform workspaces with environment-specific tfvars files. Never share one state file across environments; a mistake in dev should never be able to touch prod.
ProductionExplain the Eventarc service account race condition from this project, and why time_sleep is an acceptable production fix.
Enabling the Eventarc API triggers Google to asynchronously provision a service agent. The enable API call returns before that account is fully propagated in IAM, so an immediate IAM binding can fail. time_sleep with an explicit depends_on inserts a deterministic wait, trading a small amount of apply time for a reliable, repeatable pipeline — an acceptable and common pragmatic fix for known cloud-provider propagation delays.
Beginner → Production, in increasing order of nuance Scenario questions test debugging instincts, not memorization
