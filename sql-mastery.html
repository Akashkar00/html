Introduction to SQL

What SQL is, where it came from, how databases actually work under the hood, and the landscape of engines you'll meet in production.

1. Introduction

SQL (Structured Query Language) is the standard language for storing, retrieving, and manipulating data in relational database systems. Every time an app checks your login, a bank verifies your balance, or Netflix decides what to recommend, there's a very good chance a SQL query fired somewhere behind the scenes in under a few milliseconds.

Unlike general-purpose languages like Python or Java, SQL is declarative — you describe what data you want, not how to fetch it step by step. The database engine's query optimizer figures out the "how."

2. Why It Exists

Before SQL, developers wrote custom, imperative code to navigate hierarchical or network-style databases — every query required knowing the physical storage structure. In 1970, IBM researcher Edgar F. Codd published "A Relational Model of Data for Large Shared Data Banks," proposing that data be stored in simple tables (relations) and queried using set-based logic instead of manual navigation. SQL was born shortly after as the practical language implementing that model — freeing developers from caring about physical storage and letting them just ask questions about the data.

Why It Exists
SQL exists to separate what data you want from how it's physically stored and retrieved. This abstraction is why the same SQL skills transfer across MySQL, PostgreSQL, Snowflake, and even Spark SQL.
3. Real-World Analogy
Analogy: The Librarian
Think of a relational database as a giant, perfectly organized library, and SQL as the request slip you hand to the librarian. You don't need to know which shelf, which floor, or which box a book is in — you just write "all mystery novels published after 2015 sorted by author" and the librarian (the query engine) does the walking, searching, and sorting for you.

ACID & CAP — deeper dive

ACID is what makes a bank transfer safe:

  • Atomicity — the whole transaction succeeds or none of it does.
  • Consistency — the database moves only between valid states.
  • Isolation — concurrent transactions don't see each other's half-finished work.
  • Durability — once committed, data survives crashes/power loss.

CAP theorem (Eric Brewer) states a distributed system can only fully guarantee two of: Consistency, Availability, Partition tolerance — during a network partition, you must trade off consistency vs. availability. This is why Snowflake/BigQuery (OLAP, eventually consistent in places) behave differently from PostgreSQL (OLTP, strongly consistent).

Normalization vs. Denormalization (Overview)

Normalization organizes data to eliminate redundancy (splitting a "customer + orders" blob into separate customers and orders tables). Denormalization intentionally re-introduces redundancy — duplicating data — to make reads faster in analytics/reporting systems. We cover the full normal-form ladder (1NF→5NF) in Section 26.

16. Interview Questions
Q1. What is the difference between SQL and a RDBMS?
SQL is a language for querying relational data. An RDBMS (MySQL, PostgreSQL, etc.) is the actual software system that implements and executes that language against stored data. SQL is the "what," the RDBMS is the "how."
Q2. Explain OLTP vs OLAP with an example.
OLTP handles many short transactions (e.g., "insert this order") optimized for speed and consistency. OLAP handles fewer but much larger, complex read queries (e.g., "average order value by region for the last 3 years") optimized for throughput over huge scans, often on denormalized/columnar storage.
Q3. What are the four ACID properties?
Atomicity, Consistency, Isolation, Durability — see the deep dive box above for a full explanation of each.

Database Objects

The building blocks every relational database is made of — from a single row up to materialized views and triggers.

Introduction & Why It Exists

A relational database is organized as a hierarchy of objects. Understanding this hierarchy is what lets you reason about where data actually "lives" and how permissions, backups, and performance settings apply at each level.

Analogy: An Office Building
The Database is the building. A Schema is a floor/department. A Table is a filing cabinet. A Row is one folder in that cabinet. A Column is a labeled field on every folder (e.g., "Name," "Date"). An Index is the cabinet's alphabetical tab system that lets you find a folder without checking every single one.

Hierarchy: Database → Schemas → Tables/Views/Indexes/Sequences → Rows & Columns, with procedures/triggers attached at the schema level.

SQL Syntax, Comments & Conventions

The formatting rules and style conventions that separate readable, maintainable SQL from a wall of unreadable text.

SQL keywords (SELECT, WHERE) are not case-sensitive in any major engine — but identifiers (table/column names) can be case-sensitive depending on the database and quoting. PostgreSQL folds unquoted identifiers to lowercase; SQL Server is typically case-insensitive by default; MySQL's behavior depends on the OS and table settings.

Why Conventions Matter
A production codebase might have thousands of queries across dozens of engineers. Consistent casing and formatting isn't cosmetic — it prevents real bugs like `Users` vs `users` mismatches across environments.

Data Definition Language (DDL)

CREATE, ALTER, DROP, TRUNCATE and RENAME — the commands that shape your database's structure.

DDL statements define the shape of your data — tables, columns, constraints — as opposed to the data itself. Critically, DDL is usually auto-committed in MySQL (cannot be rolled back), while PostgreSQL and SQL Server allow DDL inside transactions.

Analogy
DDL is construction work on the building itself (adding a wall, removing a room). DML is moving furniture in and out. DQL is just looking around.

    name VARCHAR(150) NOT NULL,
    price DECIMAL(10,2) NOT NULL CHECK (price >= 0),
    category VARCHAR(50),

Why UPSERT/MERGE Exist
Without them, "insert or update" requires a SELECT to check existence, then an INSERT or UPDATE — two round trips with a race condition window between them. UPSERT does it atomically in one statement, which matters enormously under concurrent load.
Common Mistakes
Running UPDATE/DELETE without a WHERE clause (updates/deletes every row!); not wrapping multi-statement DML in a transaction; forgetting `EXCLUDED` (Postgres) or `source.` (MERGE) references when writing conflict resolution logic.
Best Practices
Always run a SELECT with the same WHERE clause first to preview affected rows before UPDATE/DELETE in production; batch huge DML operations to avoid long-held locks; use UPSERT for idempotent data pipelines.

GROUP BY collapses rows into one row per group — you lose row-level detail. Window functions let you compute aggregates "over a window" of related rows while keeping every individual row. Locking, Deadlocks & MVCC — deeper dive

Locking: databases use row/table/page locks to prevent conflicting concurrent writes. Deadlocks occur when Transaction A waits for a lock held by B, while B waits for a lock held by A — the database detects this and kills one transaction automatically.

MVCC (Multi-Version Concurrency Control), used by Postgres and MySQL/InnoDB, lets readers see a consistent snapshot of data without blocking writers — instead of locking rows for reads, each transaction sees the version of a row that existed when its transaction/statement started.

Relational databases like PostgreSQL (via the pgvector extension) now store embeddings — numeric vector representations of text/images — directly alongside regular relational data, enabling Retrieval-Augmented Generation (RAG) pipelines without a separate specialized vector database.

sql — pgvector similarity search
CREATE EXTENSION vector;
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    metadata JSONB,
    embedding VECTOR(1536)
);

SELECT id, content
FROM documents
WHERE metadata->>'category' = 'sql-docs'   -- metadata filtering
ORDER BY embedding <-> '[0.012, -0.045, ...]'  -- vector similarity (hybrid search)
LIMIT 5;

Why It Exists
Storing embeddings inside your existing relational database means RAG pipelines can filter by real business metadata (tenant_id, permissions, category) using standard SQL combined with vector similarity — avoiding the complexity of syncing data between a separate vector database and your source of truth.
Performance Notes
Approximate nearest-neighbor indexes (like HNSW or IVFFlat in pgvector) trade a small amount of accuracy for dramatically faster vector search at scale — a full linear scan over millions of embeddings is far too slow for production RAG.

SQL Interview Preparation

Curated, high-signal interview questions spanning beginner to advanced difficulty, with full explanations.

Beginner Level
1. What is the difference between DELETE, TRUNCATE, and DROP?
DELETE removes rows selectively and logs each row (rollback-able). TRUNCATE removes all rows instantly with minimal logging. DROP removes the entire table structure permanently.
2. What is a primary key and can a table have more than one?
A primary key uniquely identifies each row and cannot be NULL. A table can have only ONE primary key, but that key can be composite (span multiple columns).
3. What's the difference between WHERE and HAVING?
WHERE filters individual rows before grouping; HAVING filters grouped results after aggregation and can reference aggregate functions.
4. What does a LEFT JOIN return that an INNER JOIN doesn't?
LEFT JOIN returns every row from the left table plus matches from the right (NULLs if none), while INNER JOIN returns only rows with matches in both tables.
5. Why does `= NULL` never match anything?
NULL represents "unknown." Any comparison operator against NULL evaluates to UNKNOWN, not TRUE — you must use IS NULL / IS NOT NULL instead.
Intermediate Level
6. How would you find the second-highest salary without LIMIT/OFFSET?
SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees); — or use DENSE_RANK() and filter rank = 2, which handles ties more robustly.
7. Explain the difference between UNION and UNION ALL.
UNION removes duplicate rows across the combined result sets (requires a sort/dedup step); UNION ALL keeps all rows including duplicates and is faster since it skips deduplication.
8. What's a self-join and when would you use one?
A self-join joins a table to itself, typically via aliases. Common use: employee-manager hierarchies, finding duplicate rows, or comparing rows within the same table.
9. How do indexes speed up SELECT but slow down INSERT/UPDATE?
Indexes let reads skip full table scans via structures like B-trees. But every write must also update each affected index, adding overhead proportional to the number of indexes on the table.
10. What's a CTE and why prefer it over a nested subquery?
A Common Table Expression (WITH clause) names an intermediate result, improving readability over deeply nested subqueries, and enables recursion which subqueries alone cannot do.
Advanced Level
11. Explain MVCC and why Postgres/MySQL InnoDB use it.
MVCC (Multi-Version Concurrency Control) lets readers see a consistent snapshot of data without blocking concurrent writers, by keeping multiple row versions rather than locking rows for every read.
12. How would you design a schema to support both high-frequency writes and complex analytics?
Use a normalized OLTP database for writes, then replicate/stream (CDC, ETL/ELT) into a separate OLAP warehouse for analytics, isolating the workloads so heavy reporting queries never impact transactional latency.
13. What causes a deadlock, and how do you handle it in application code?
Deadlocks occur when two transactions each hold a lock the other needs. The database detects the cycle and aborts one transaction; the application should catch that specific error and retry the transaction.
14. How would you paginate efficiently through 100 million rows?
Use keyset (cursor-based) pagination — filter WHERE id > last_seen_id ORDER BY id LIMIT n — instead of OFFSET, which requires scanning and discarding all skipped rows.
15. Walk through how you'd diagnose a sudden production query slowdown.
Check EXPLAIN ANALYZE for plan changes, verify statistics freshness (ANALYZE), check for lock contention/blocking queries, review recent data volume growth or index drops, and check replication lag if reading from a replica.
Interview Tip
Always narrate your thought process out loud — interviewers care more about how you reason about tradeoffs (indexes, normalization, isolation levels) than about memorized syntax.

Worked Solution: #6 Second highest salary per department
WITH ranked AS (
  SELECT department, name, salary,
    DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rnk
  FROM employees
)
SELECT department, name, salary FROM ranked WHERE rnk = 2;

DENSE_RANK handles ties correctly (if two people tie for highest, the next distinct salary is still rank 2), which a naive LIMIT/OFFSET approach would get wrong.

Production Case Studies Across Industries

How the concepts from this entire course combine to solve real domain-specific problems.

E-commerce
Product catalog (normalized), inventory (row-level locking on checkout), order history (partitioned by month), recommendation queries (window functions for "customers also bought"). Key challenge: preventing overselling under concurrent checkouts — solved with row-level locks or optimistic concurrency (version columns).
Banking
Double-entry ledger tables with strict ACID transactions, immutable append-only transaction logs, strong isolation levels (often Serializable for transfers), heavy audit trail requirements. Key challenge: guaranteeing money is never created or destroyed — enforced via CHECK constraints and transactional atomicity.
Healthcare
Patient records with strict access control (row-level security by clinician), encrypted PII columns, full audit logging of every read/write for compliance (HIPAA-style regulations). Key challenge: balancing query performance with mandatory field-level encryption/masking.
Inventory
Multi-warehouse stock tracking, triggers to prevent negative stock, materialized views for real-time stock-level dashboards. Key challenge: reconciling stock counts across warehouses with eventual consistency during high-volume sales events.
HR
Employee hierarchy (self-joins/recursive CTEs for org charts), payroll calculations (careful DECIMAL usage), historical salary tracking (temporal tables / effective-dated rows). Key challenge: querying "who reported to whom on a specific past date" — solved with effective-date ranges rather than mutable current-state columns.
Social Media
Feed generation (fan-out on write vs. read), follower graphs (many-to-many join tables), engagement analytics at massive scale (OLAP warehouses, pre-aggregated rollups). Key challenge: scaling "who does X follow" queries to billions of edges — often requires moving beyond pure relational modeling into specialized graph/cache layers.
Ride Sharing
Geospatial matching (driver-rider proximity), time-series trip data (partitioned by date), dynamic pricing calculations. Key challenge: extremely high write throughput for location updates — handled with in-memory stores feeding into SQL for durable/analytical records.
Streaming
Watch history and recommendation features, content metadata (normalized catalog + denormalized search index), viewing analytics (huge OLAP fact tables). Key challenge: querying "what should we recommend next" combines SQL aggregation with ML feature pipelines built on top of SQL-queried data.
The Common Thread
Every one of these systems combines the same fundamentals from this course — normalization for correctness, indexes for speed, transactions for safety, and window functions/aggregation for insight — applied with domain-specific judgment about where to bend the rules (denormalize, cache, shard) for real-world scale.
